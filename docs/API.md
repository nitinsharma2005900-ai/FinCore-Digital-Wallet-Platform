# API behavior and financial contracts

Interactive Swagger is served at `/api-docs`. The source-generated OpenAPI 3.1 document is `docs/openapi.json`; generate it with `npm run docs`. The Postman collection and environment are in `postman/`. The selected localhost API port is recorded in `.env`; this installation uses 4001 because 4000 is occupied.

Authentication: register/login returns an access JWT valid for ten minutes. Send it in `Authorization: Bearer ...`. The HttpOnly refresh cookie lasts seven days. Refresh requires a trusted Origin and rotates the session. Reusing a revoked refresh cookie revokes the entire token family. Logging out revokes the family. Resource lookups use the authenticated user's ownership, never a caller-supplied owner ID. Simulated MFA is single use, expires after five minutes, and locks after five failures. Local simulation codes are shown explicitly; production activation is blocked until secure delivery is configured.

Sensitive actions require `/auth/reauthenticate` with the current password and the returned five-minute token in `X-Reauth-Token`. A transfer additionally requires `confirmation: true`. Monetary JSON values must be strings, for example `"12.34"`, never JSON floating point numbers. Only INR is currently enabled. Maximum transfer/funding amount is INR 10,000,000.00. Internal wallet transfer fees are zero; Python supports configurable Decimal fee and interest calculations separately.

Success responses are `{data,meta?,requestId}`. Errors are `{error:{code,message},requestId}`. Use 401 to sign in again, 403 for permission/reauthentication/origin rejection, 404 for missing or inaccessible resources, 409 for state or idempotency conflict, 422 for invalid amounts/insufficient funds, 429 for rate limiting and 503 for dependency unavailability. Never infer payment success from an HTTP timeout: inspect the existing operation and retry with the same key.

Transfers require an `Idempotency-Key` of 8–128 characters. Keys are scoped to the caller. The stored hash binds source, recipient, normalized amount, currency, kind, description and original transaction. Replaying the same request returns the same transaction; different content returns 409. Funding intents use a deterministic user/key ID and the same provider idempotency key. A successful provider settlement is unique per intent and cannot credit twice.

Lifecycle: financial journal transactions are inserted PENDING, gain exactly one debit and one credit, then become POSTED inside a single database transaction. PENDING/FAILED transactions cannot retain entries at commit. POSTED headers and entries cannot be modified. Payment intents are independently PENDING, FAILED or SUCCEEDED. A late success may recover a prior failed provider attempt; a failure never overwrites a success. Refunds and reversals create a compensating transaction referencing the original, with at most one full compensation. Partial refunds and multiple currencies are outside the current scope.

Wallet liability semantics: CREDIT increases the wallet balance; DEBIT decreases it. Treasury is the synthetic counterparty. Settled balance = sum(credits) − sum(debits). Available balance = settled − active holds. Source/destination locks are acquired in ascending ID order, then balance checks and posting occur in READ COMMITTED. Deferred PostgreSQL constraints reject unbalanced transactions and negative customer availability even if the API path is bypassed. Runtime credentials cannot disable constraints or edit historical journal entries.

Local webhook signature: `X-Fincore-Signature: t=UNIX_SECONDS,v1=HEX_HMAC`. HMAC-SHA256 signs `timestamp.raw_body` with LOCAL_WEBHOOK_SECRET. Verification uses the exact request bytes and a five-minute time tolerance. Event IDs are deduplicated; replay is recorded in audit history. Reuse with a different intent/type/amount returns conflict. Amount mismatches are persisted without crediting funds. Stripe mode uses Stripe-Signature and the Stripe SDK's raw-byte verification; live events and live secret keys are rejected.

Stripe test mode requires `PAYMENT_PROVIDER=stripe`, `STRIPE_SECRET_KEY=sk_test_...`, `STRIPE_WEBHOOK_SECRET=whsec_...` and a public `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_...`. Create a test intent, confirm its clientSecret using Stripe.js, and forward signed test events to `/api/v1/webhooks/payments`. The local simulator is separate and never described as an externally verified integration. External refund requests reserve customer funds in a hold, queue an idempotent provider refund, then release the hold and post the compensation atomically. Failed jobs retain the hold for investigation; an administrator can retry the same durable request.

Transactions accept page (starting at 1), limit (1–100), search, sort=asc/desc, kind and status. Disputes and notifications accept page/limit. Staff result sets are bounded to 100 rows; reconciliation processes the newest 1000 intents per run. These limits are explicit capacity limits for the educational dataset.

Statements require walletId, from and to in YYYY-MM-DD. Boundaries are UTC and inclusive; maximum range is 366 days and 100000 journal lines. JSON includes opening/closing balances, debit/credit totals and activity. CSV protects cells against spreadsheet formula execution. PDF and CSV are downloaded from the same endpoint using format=pdf/csv. They use stored synthetic journal data and Python summary calculations.
